# MASTER DEVELOPMENT PROMPT

## Project: Intelligent Offline Document & Book Formatting Platform

Build a **production-grade, commercially sellable, fully offline desktop software application** for intelligent document analysis, structural understanding, automatic book formatting, and professional template-based publication.

The application must be capable of processing **very large Microsoft Word `.docx` manuscripts, including documents of approximately 10,000 pages or more**, without crashing, freezing the UI, unnecessarily consuming all available RAM, or requiring cloud services.

The software should feel like a polished commercial desktop product similar in usability, reliability, project management, reporting, and professional UX to established document-analysis software such as WCopyfind, while focusing on **intelligent manuscript understanding and publication formatting**.

The system must be designed from the beginning so that it can evolve from a hackathon prototype into a real commercial product.

---

# 1. CORE PRODUCT VISION

The application is an:

> **Offline Intelligent Document Understanding and Book Formatting Platform**

The user should be able to:

1. Create a project.
2. Import a `.docx` manuscript.
3. Analyze the document.
4. Automatically identify its logical structure.
5. Detect chapters, headings, subheadings, body text, quotes, captions, lists, tables, images and other document elements.
6. Select a default formatting template OR create/use a custom template.
7. Automatically transform the manuscript according to the selected template.
8. Handle very large manuscripts through chunked and parallel processing.
9. Preview the result.
10. Review uncertain AI/ML decisions.
11. Correct decisions manually.
12. Save those corrections locally.
13. Reuse templates.
14. Export a publication-ready `.docx`.
15. Eventually support PDF and EPUB export.

The core system must work **without external AI APIs, cloud processing, or internet access**.

# 2. NON-NEGOTIABLE REQUIREMENTS

The following requirements are mandatory.

## 2.1 Offline

The document-processing pipeline must work completely offline.

No dependency on:

* OpenAI APIs
* Gemini APIs
* Claude APIs
* Cloud LLMs
* Cloud NLP APIs
* Cloud document-processing APIs
* Firebase
* Supabase
* AWS processing
* Azure processing
* Google Cloud processing
* Any external API for manuscript analysis

The manuscript must never need to leave the user's computer.

---

## 2.2 Large Document Support

The architecture must support:

* 100-page documents
* 500-page documents
* 1,000-page documents
* 5,000-page documents
* 10,000+ page documents

Do not design the system around loading and processing the entire manuscript as one massive in-memory object.

Use:

* document indexing
* logical chunking
* persistent intermediate state
* worker pools
* multiprocessing
* controlled memory usage
* incremental processing
* incremental result storage
* crash recovery

---

## 2.3 UI Must Never Freeze

Heavy document processing must never execute directly on the UI thread.

The interface must remain responsive while processing.

The user must be able to:

* view progress
* cancel jobs
* pause jobs where possible
* resume jobs
* inspect errors
* continue using non-processing parts of the application

# 19. CONCURRENCY MODEL

Use two concurrency mechanisms.

## ThreadPoolExecutor

Use threads for:

* file I/O
* cache operations
* preview generation
* reading/writing
* background non-CPU tasks

## ProcessPoolExecutor / multiprocessing

Use processes for:

* CPU-heavy feature extraction
* NLP
* ML inference
* expensive formatting
* document analysis

Architecture:

```text
                  JOB MANAGER
                       │
            ┌──────────┴──────────┐
            │                     │
       THREAD POOL           PROCESS POOL
            │                     │
        I/O Tasks          ML / NLP / CPU
        Cache              Formatting
        Preview            Analysis
```

Do not use threading as a substitute for CPU parallelism.

# 27. LLM POLICY

The core formatting engine must not depend on an LLM.

No cloud LLM.

No external LLM API.

No requirement for an internet connection.

An optional local LLM may be introduced in a future version for non-critical assistance such as:

* metadata suggestions
* document summaries
* semantic assistance

but formatting and structural decisions must remain functional without it.

The original project specifically establishes a no-cloud/no-LLM direction.
